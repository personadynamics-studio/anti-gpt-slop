# AI 交付物瑕疵簽名庫（Anti GPT Slop）

[![GitHub stars](https://img.shields.io/github/stars/personadynamics-studio/anti-gpt-slop?style=flat&label=stars)](https://github.com/personadynamics-studio/anti-gpt-slop/stargazers)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)
[![Signatures](https://img.shields.io/badge/signatures-48-critical.svg)](SKILL.md)
[![Cases](https://img.shields.io/badge/cases-12%20append--only-informational.svg)](SAMPLES.md)

**English** — A signature library and scanning procedure for auditing AI deliverables. It carries 48 family signatures of low-quality or self-authorized code plus an append-only case ledger; any hit that cannot produce four pieces of evidence — necessity, blast radius, pre-existing checks, and a real interception — is rejected. It works in DeepSeek Harness, Codex, Claude Code, and any agent that reads `SKILL.md`.

**中文** — 本技能用於審核自動化編碼代理之交付物：48 條瑕疵家族簽名，外加一本 append-only 案例紀錄。命中而無法提出四項舉證者，一律退回。

判定依據為可觀察的程式形狀與證據缺口，不作動機推測，亦不作文字風格評論。

## 公開版說明

本倉庫為去識別化公開版。案例紀錄僅保留可觀察之程式形狀與舉證結構，不載任何真實專案名稱、檔案路徑、行號或事故編號；行文採書面語。私有詳細版（含完整指紋）另行保管，不在本倉庫內。

## 它治什麼病

| 病灶 | 現形方式 |
| --- | --- |
| 假完成 | 刪幾行即稱修復、未執行之資料庫指令即稱已生效、靜態閱讀即稱實際運行 |
| 自製認證標記 | 資料已正確讀取，卻因缺少自行發明之印記而不放行 |
| 第二份真相 | 同一條規則於資料庫、應用層與前端各抄一份互相檢查 |
| 責任漂移 | 將業務政策寫入資料庫或前端，將明確命令丟回模型決定 |
| 粉飾結果 | 未知寫成已停止、`ERROR` 之後仍送 `DONE`、缺值自動補預設 |
| 保留理由堆疊 | 可疑機制旁出現成堆「因為…必須保留」之自述，無一句能對應需求來源 |

## 怎麼運作

### 掃描前必備三項（缺一不得開始）

1. **交付清單**：版本控制輸出之原文（例如 `git show --stat`、`git diff`），而非交付方之自述。
2. **聲明原文**：交付方對「做了什麼、為何如此」之原始敘述。
3. **逐項證據**：每一主張所對應之檔案、行號與原文。

### 四項舉證（命中後逐項回答；缺一即視為未舉證）

| # | 題目 | 答不出時之寫法 |
| --- | --- | --- |
| 1 | **必要性**：該控制之產品需求來源何在（需求方原話／平台官方文件／實際事故編號）？ | 明寫「無需求來源」 |
| 2 | **失敗範圍**：該控制失效時阻斷何事？被阻斷之初始化、服務路徑與介面須逐項列出 | 不得僅寫「阻斷啟動」 |
| 3 | **既有核對**：同一保證原本由哪個函式、介面或資料表負責？新增部分之獨有差異為何？ | 說不出獨有差異即未舉證 |
| 4 | **實際攔截**：是否曾有實際事件被該控制阻擋（附原始紀錄）？ | 無者明寫「無」，不得以「它具備拒絕能力」替代 |

### 判定與處置

| 情形 | 處置 |
| --- | --- |
| 命中 ＋ 四項舉證有缺 | **退回該項**：不得進入下一輪施作，不得視為已交付；應要求補足證據或撤回 |
| 命中 ＋ 四項齊備 | 可收，並將四項答案寫入驗收紀錄（位置、檢查項目、退回後果、信心程度、由誰讀過哪一行） |
| 未命中 | 僅能記載「本輪簽名庫未命中」，不得寫「乾淨」「無問題」 |
| 誤報 | 對造提出檔案、行號與原文證明為誤報 → 收窄該簽名形狀，並於 `SAMPLES.md` 記載一次誤報；紀錄不得刪除 |

## 實例（節錄自 [`SAMPLES.md`](SAMPLES.md) 案例 005）

**輸入**：一份庫存報告，其中兩項聲稱「續頁游標綁定查詢印記，以防止續頁位置錯配」與「原文續讀必填摘要」。

**掃描結果**

- 命中 **SIG-29 自算查詢摘要作為續頁資格憑證**，兼中 SIG-06（以摘要當驗證）、SIG-13（以拒絕代替修復）、SIG-26（無來源即事故）。
- 必要性＝**無**：無需求方原話、平台強制條文或事故單要求該摘要與必填欄位。
- 失敗範圍＝合法續頁與續讀被拒：同一組過濾條件只要空白、順序、預設值或時間格式不同，重算摘要即不同。
- 既有核對＝資料庫端擁有者過濾與查詢介面自身之游標；續讀已有範圍檢查，摘要未新增原子性保證。
- 實際攔截＝**無紀錄**。
- 判定：**列為不合格**，進入刪除清單。
- 界線：只讀；未執行產品、未呼叫工具或模型；「將阻斷合法請求」為靜態推斷。


## 使用

直接點名：

```text
載入 gpt-slop-signatures，掃描這次提交是否含有本庫所列之瑕疵簽名。
```

或以白話提出：

```text
檢查這次交付是否含有可疑或無來源的控制機制，以及是否自行加入了多餘關卡。
```

審核輸出必須包含：**位置、檢查項目、退回後果、信心程度、核實方式（由誰讀過哪一行）**。對造主張判斷有誤時，應要求其提出檔案、行號與原文；證實為本方之誤，則撤回該條並寫明撤回內容。

技能另附**常見說詞與應提證據對照表**：聽到「已修復／已涵蓋／原始碼完成／大方向正確、細節待補／分類不可靠／建議下一步」時，當場應要求何種證據。詳見 [`SKILL.md`](SKILL.md) 第 6 節。

## 48 條家族簽名

| 編號 | 名稱 | 形狀 |
| --- | --- | --- |
| SIG-01 | 於必要初始化之前插入額外控制 | 新增之外部檢查置於 `initialize()`／lifespan 之前，失敗即拋出錯誤 |
| SIG-02 | 自行建立第二份預期狀態 | 將遠端狀態複製為資料庫以外之副本，再要求兩者完全相等 |
| SIG-03 | 以拒絕運作代替交付 | 依賴產物尚未產生，先將缺失時之錯誤接入正式入口 |
| SIG-04 | 重複既有核對而未說明新增保證 | 原有身分、版本、健康核對之外再增一層，卻說不出多出何種保證 |
| SIG-05 | 將作業系統拓樸條件混入業務可用性 | 固定絕對路徑、目錄擁有者、禁止符號連結等被寫成啟動資格要件 |
| SIG-06 | 以權威名稱代替實質驗證 | `trusted`／`verified`／`provenance` 實際僅驗證格式、非空或相等 |
| SIG-07 | 使未交付之外部產物成為必要依賴 | 程式硬性依賴交付文件自承「尚未產生」之產物 |
| SIG-08 | 以無關故障佐證或歸咎新增控制 | 堆疊追蹤終止於他處，卻陳述為新控制攔截成功或由其造成事故 |
| SIG-09 | 以常識性說詞代替必要性說明 | 僅以「保險起見／順手加上／業界慣例」作為新增必填之理由 |
| SIG-10 | 先將實作寫入文件，再以文件為實作授權 | 新限制先寫入規則或手冊，其後引用該條文證明「本來即要求」 |
| SIG-11 | 以間接證據宣稱當次實際運行 | 以原始碼已改、差異核對、健康檢查就緒冒充當次實際運行 |
| SIG-12 | 同一事實存在兩份可執行權威 | 前端重算額度、資料庫與應用層各持一份政策 |
| SIG-13 | 以新增拒絕條件代替修復 | 資料已正確讀取，卻因缺少自製印記或額外驗證器而不放行 |
| SIG-14 | 將未知或失敗結果呈現為成功 | 未知寫成已停止、`ERROR` 後仍送 `DONE`、缺值自動補預設 |
| SIG-15 | 僅修改單一入口，舊路徑仍然放行 | 新條件僅加於 A 路徑，恢復流程、舊呼叫端或另一模式仍放行 |
| SIG-16 | 以重試、降級或吞除錯誤掩蓋確定失敗 | 永久性契約錯誤仍進入退避重試；捕捉例外後填入空集合 |
| SIG-17 | 以新增框架或第二執行環境代替最小修復 | 出現第二個執行環境，或新層無消費者而舊路徑仍在運行 |
| SIG-18 | 無消費者之欄位與反向誤刪 | 欄位僅有寫入而無讀取；或清理時刪除仍有呼叫端之操作 |
| SIG-19 | 使用過期或時點混雜的快照 | 非同步等待後仍用舊身分快照；同次提交混用兩份不同時點之讀取 |
| SIG-20 | 將業務政策寫入 SQL 或前端 | 價格、額度、方案、解鎖或重試決策出現於資料庫指令或前端 |
| SIG-21 | 依賴與設定可隨時間漂移 | `>=`、`--upgrade`、CDN 版本標籤、模組載入期間讀取設定 |
| SIG-22 | 以固定數值遮蔽版面衝突 | 為掩蓋重疊而加固定內距或高度，或以容器層級 `overflow:hidden` 遮蔽 |
| SIG-23 | 將「已讀取或存在」視為「可用或已採用」 | 讀取即寫入參照；後端入口存在即宣稱網站可用 |
| SIG-24 | 未經授權擴大範圍並自我批准 | 將未經批准之差異混入提交；自產清單或印記用以證明自身 |
| SIG-25 | 交付聲明未交代已執行與未執行項目 | 報告僅列修改內容；或已載明未執行卻仍要求驗收通過 |
| SIG-26 | 以「未觀察到誤擋」作為放行理由 | 以「尚無真實請求觸及」將原始碼已證實之自製拒絕條件降級 |
| SIG-27 | 來源混同 | 可追溯之原流程與後加之自製條件共用一個名稱，互相背書 |
| SIG-28 | 以大量保留理由製造授權外觀 | 可疑機制旁成堆「保留…」理由，無一句能對應原話、平台條文或事故編號 |
| SIG-29 | 自算查詢摘要作為續頁資格憑證 | 應用自算查詢摘要置入游標，下次請求重算不等即拒絕 |
| SIG-30 | 自證清單作為准入權威並以不可變鎖保護 | 自採自比之清單升為就緒與准入條件，再以不可變觸發器鎖住 |
| SIG-31 | 跨語言同構摘要契約由雙方各自實作並逐次重算 | 應用層與資料庫各實作一次規範化內容與摘要，資料庫逐次重算並拒絕 |
| SIG-32 | 修復前置條件要求待修狀態先符合期望 | 修復腳本要求現狀先符合目標，真正漂移之資料庫被自身擋下 |
| SIG-33 | 版本事實散落多處並以等值約束與不可變觸發器固定 | 版本號散見多處，其中一份被等值約束與不可變觸發器釘死 |
| SIG-34 | 以保存「未知」代替修復生產者 | 自家生產者可證地寫出矛盾組合，改在資料層把「未知」升格為合法狀態 |
| SIG-35 | 以覆述需求代替交付方案 | 答覆是需求方原話的改寫加口號，全文無檔名、行號、原文引用 |
| SIG-36 | 自述與版本事實相反 | 號稱撤回、差異實為淨增；或自稱未提交而提交已存在 |
| SIG-37 | 以正確原則句為新增入口背書 | 原則正確，但句中那個「第二入口」當時並不存在 |
| SIG-38 | 無承載點、無期限的等待 | 聲明等待外部通知，未寫承載點、期限、對外回應與永不送達的收尾 |
| SIG-39 | 跨業務循環的責任混同 | 甲循環的方案裡出現乙循環的身分與恢復語義 |
| SIG-40 | 將「無法精確結算」替換為「不必結算」 | 停止先把收據來源關掉，再把缺證寫成能力極限；未確認永久存在 |
| SIG-41 | 以新增分支覆蓋舊分支（加法式修復） | 不替換原分支，另加一條分支執行新行為，同一狀態兩套渲染 |
| SIG-42 | 以不可見能力之名保留死模板 | 保留永不顯示的模板，理由是裡面有個不可達按鈕代表「能力」 |
| SIG-43 | 以材料中未出現代替需求撤銷之授權 | 樣本裡沒有某功能，即宣告該需求自本期基準撤出 |
| SIG-44 | 以無文字衝突代替架構相容（錯誤基線） | 以「檔案沒有直接衝突、補丁套得上」當作架構相容 |
| SIG-45 | 將字面內容放入會被語法掃描的容器 | 原文寫入會被模板引擎掃描的欄位，雙大括號被當變數插值 |
| SIG-46 | 以過寬的未知分類吞併已證明未執行之失敗 | 空呼叫即判用量未完成，並以測試把阻塞結果定義為通過 |
| SIG-47 | 將經否定的等待路徑保留為另一必要例外 | 被否定的等待改名為「只在必要時」的例外而復活 |
| SIG-48 | 為無來源前提補防護，使該前提更難糾正 | 先增設無來源依賴，再為它補防重、補身分、補費用邊界 |

批次與來源：SIG-01～SIG-10 歸納自一件「以外部安裝身分檔作為啟動前置」之案例；SIG-11～SIG-25 歸納自一份內部缺陷紀錄與版本歷史；SIG-26～SIG-27 來自一件驗證中介層之來源歸屬爭議；SIG-28～SIG-30 分別來自保留理由堆疊、自算查詢摘要與自採自比清單三案；SIG-31～SIG-33 來自同一批資料庫稽核；SIG-34～SIG-39 來自一件付款鏈案例；SIG-40 來自一件「停止後用量未確認」案例；SIG-41 與 SIG-42 來自同一件前端結果框拆除案（兩輪自述）；SIG-43～SIG-48 來自一份第三方鑑證報告所引之指紋（其中 SIG-45、SIG-46 另有提交級核實）。逐條之形狀、觸發詞、當場檢查與判定，見 [`SKILL.md`](SKILL.md)。

掃描優先序：先掃 SIG-11、SIG-15、SIG-20、SIG-13（歷史上最常見）；文件出現成堆「保留／維持原狀」時先掃 SIG-28；見到自算查詢摘要或游標印記時先掃 SIG-29；見到自採自比、不可變、無升級入口之清單時先掃 SIG-30；見到應用層與資料庫兩邊各自重算同一摘要時先掃 SIG-31；見到修復或同步腳本自帶前置拒絕時先掃 SIG-32；見到版本號散落又被等值約束固定時先掃 SIG-33；見到「把可確定的事保存成未知」時先掃 SIG-34；答覆通篇口號而無檔名行號時先掃 SIG-35；自述撤回或拔除時先要版本差異統計再掃 SIG-36；出現「等待外部事件」時先掃 SIG-38；出現「停止或取消之後無法結算、用量未確認」時先掃 SIG-40；出現「保留舊分支、再加一條分支」時先掃 SIG-41；出現「保留恢復能力」當保留理由時先掃 SIG-42；起分支前只核過檔案衝突時先掃 SIG-44；把原文寫進會被模板掃描的欄位時先掃 SIG-45；見到「空用量一律視為未完成」或新增測試把阻塞寫成通過條件時先掃 SIG-46；為一條無來源依賴補防重、補身分、補費用邊界時先掃 SIG-48。

## 案例紀錄

新形態命中且不在表上時，當場新增 `SIG-xx`（形狀／觸發詞／當場檢查／判定），並於 `SAMPLES.md` 追加一筆。**不得僅於對話中提及即視為登錄；紀錄不得刪除，誤報亦須保留。**
